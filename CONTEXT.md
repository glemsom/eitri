# Eitri — Domain Glossary

Canonical terms for planned Eitri (single-binary AI coding agent for Linux).

- **Workspace** — the user's working directory in which Eitri reads, writes, and executes; mounted read-write at its host path inside the sandbox.
- **Path namespace** — the view of the filesystem a component operates in. Host paths are canonical; the only remapped region is the session temp (`/tmp` ↔ host `/tmp/eitri-<GUID>`). See ADR-0002.
- **Session temp** — per-run ephemeral `/tmp` shared by `bash` and host-side tools; removed at run end.
- **Sandbox / bwrap cage** — the bubblewrap isolation boundary for shell commands; root read-only, workspace + session temp writable, separate PID namespace, fresh pid-scoped `/proc`, private devtmpfs `/dev` with writable `/dev/shm`.
- **Host-side tool** — a tool running outside the bwrap cage but resolving the same path namespace as `bash` (e.g. `read`, `write`, `edit`, `open_in_browser`). Write-side tools (`write`, `edit`) also gate targets on the writable roots; `read` and `open_in_browser` are read-only and resolve through the shared translator alone.
- **Slash-skill activation** — a human-invoked skill trigger from the TUI via `/skillname [<args>]`, distinct from the model's automated `skill` tool call. The activation run produces a structured payload (`<skill_content>` plus optional `<skill_resources>`). Every `/skillname` starts an agent turn with the payload folded into the single high-priority **user** message that carries the prompt, with explicit binding framing ("the user invoked this skill by name; follow its instructions exactly") — the trailing args become the turn prompt, and a bare `/skillname` (no args) falls back to a default `apply the <name> skill` prompt, matching Pi's `/skill:` expansion instead of stopping after an activation note. The payload is delivered once via injection (no duplicated assistant note). Delivering the directive in the user layer (adjacent to the prompt) rather than as a competing second `system` message lets it outrank the Eitri persona when instructions conflict — smaller models deprioritize conflicting instructions received as a system message. Session compaction keeps the skill-carrying leading user message in the stable head alongside the system prompt and the `Prune` ring-fence (`isSkillMessage`) recognizes the `<skill_content>` directive in the user layer, so a slash-skill stays effective across eviction-and-summary and the model never forgets it is following the skill mid-run. A repeated `/skillname` (issue #460) **re-applies** the full payload rather than no-op'ing: the slash surface activates through a force-re-inject path (`Registry.ActivateSkill`, distinct from the model-tool `skill` call) that bypasses the session-lifetime `IsActive` dedupe — each slash is an explicit new command whose prompt messages are rebuilt fresh each turn, so the second slash must deliver the skill body again. The dedupe still guards the model's *automatic* `skill` tool call within one agent turn-loop, never fewer re-injections for a human slash.
- **Drag selection** — the width-aware click-drag copy seam lives in its own module (`internal/tui/selectionweaver.go`, issue #464): the `selectionWeaver` value type owns the selection store (the active flag plus the anchor/end cell range), the rune-index conversion (`colToRuneIndex`), and the rune-space highlight/copy operations (`highlight`, `coveredLines`, plus the `highlightRange`/`ansiStrip`/`consumeEscape` helpers). Selection coordinates are **rune-indexed and width-aware**: a mouse cell arrives in screen display-width space, `colToRuneIndex` converts it to a rune index into the plain line, and highlight and copy both operate in that same rune space — never in display-width or byte space — so wide/multibyte characters (CJK, emoji, unicode arrows, smart quotes) are selected, highlighted, copied, and pasted exactly, with no boundary split or under-coverage. The seam is a pure value type: the Model/Transcript seed it via `start`/`move`, feed it the plain content lines, and read back highlighted/copied text, so it is unit-testable on its own with no Transcript scaffolding.
- **Scroll-region seam** — the one region computation lives in its own module (`internal/tui/scrollreg.go`, issue #463): the `scrollRegionHeight` function (terminal height minus the fixed bottom band), the `scrollRegion` value type's hit-test (`contentLineAtScreenRow`: is a screen row inside the history region, and which content line does it map to) and its region-membership check (`inRegion`: is a screen row within the persisted region at all). The Transcript is a thin delegate: `scrollRegionHeight` passes the terminal minus band into the free function, and `scrollRegion()` assembles the seam value from the persisted viewport's height/offset plus the plain content-line count. The render path sizes the persisted history viewport through the same seam, and both mouse inputs route through it: click-drag selection (`mouseToContent`) maps rows through the already-rendered window, and wheel scrolling (`navigateMouse`) only scrolls when the pointer is over the region — neither re-derives the region from Model width math, so one region source serves render, drag, and wheel, and drag coordinates and on-screen rows can never drift apart.
- **Scroll / follow** — the history viewport's auto-follow behavior for long streams (issue #435): while a turn streams, `histFollow` pins the viewport to the newest content every render (`renderHistoryViewport` → `GotoBottom`), so a long merged flow stays on the active content and the user always sees the latest tool call / answer land. Scrolling up to read an earlier result (PgUp/Home or wheel-up, via `navigateHistory` / `navigateMouse`) breaks follow and the reading position then holds while the stream keeps producing below; a keypress that reaches the newest content (PgDn at the bottom, or End) re-engages follow to the bottom, as does starting a fresh turn (`submit` sets `histFollow = true`). Follow is off while paused, so new deltas never yank the viewport away from the result the user is reading.
- **Tool-result byte cap** — the shared byte budget (`DefaultByteCap`, 64 KiB) every tool result is measured against at the tool-result boundary before its bytes enter message history: over-budget results are deterministically head-truncated with an explicit `+N bytes truncated` marker (composing with the line compressor's `+N more` marker into a merged `+N more, +B bytes truncated` tail — never silent), while the full raw result stays available through the TUI expand seam (`ToolResultEvent.Result`), so only the *delivered* form is capped.
- **Expanded-view mode** — the persistent Ctrl+E transcript mode (`expandAll`) that renders every tool entry full-size. In the mode, an `edit`/`write` card replaces its raw result dump with an **inline card diff**: the entry's captured before→after file content runs through the pure-Go diff engine (`internal/diff`) and the inline card diff styling (`renderDiff`, `renderWordDiff`, homed in `internal/tui/diff.go`) inside the card's category-colored left border. A path whose content the engine couldn't snapshot falls back to the `[+N, −M]` count summary. Collapsed, the card keeps today's one-line `[+N, −M]` delta tag and never leaks file content. Ctrl+E (or the `e` expand-all key, which sets the same mode) is the **single expansion mechanism**: the modal changed-file review overlay and its Ctrl+D toggle are gone, so Ctrl+D is deliberately unbound (it reads as "exit" in other tools) and file-change inspection happens only in-flow on these expanded cards.
- **Thinking suppression** — the per-provider capability to actually stop chain-of-thought on the wire when the thinking toggle is off, declared through the generation-control seam (`GenerationControlThinkingSuppression`, negotiated via `NegotiateGenerationControls`). The two expression forms are both suppression: the openai-compatible path (opencode-go / custom-openai) **omits** the `thinking` toggle when off, while the copilot path sends an explicit `thinking:{type:disabled}`. A provider that does not declare the control surfaces a settings-panel warning that reasoning cannot be disabled instead of silently no-op'ing the toggle.
- **open_in_browser escape hatch** — deliberately **dropped**. The modal review panel's `o` key that handed the focused changed file to the host browser/editor was the only consumer of the TUI's `OpenInBrowser` dependency seam, so both went with the panel. The standalone `open_in_browser` host-side tool (registry-backed) remains for model-invoked opens.
- **Stopped turn** — a running agent turn aborted by the user (esc or ctrl+c in the TUI) at the context-cancellation boundary: the provider stream dies and any running tool is killed, and the engine refuses to open fresh provider work. The partial output already produced stays on screen in its own pane with a stopped marker — distinct from an error — and the next prompt runs normally. The TUI owns the cancel handle; the shared run seam (`runAgent` in `internal/app`) threads that per-turn cancelable context into `Engine.RunAgent` so the stop reaches the engine — batch passes `context.Background()` (non-interactive, no stop binding); the engine reports the stop through a sentinel (`ErrStopped`, wrapping `context.Canceled`) that the app adapter maps to the TUI's `Stopped` result flag so the two layers stay decoupled.
- **TurnDispatch** — the TUI module (`internal/tui/turn_dispatch.go`) owning the turn state machine: context lifecycle for each agent turn (install, cancel, release), streaming delta accumulation into the in-progress assistant message, and `turnDoneMsg` reconciliation (stopped, error, success with or without streaming). Depends on the **Turn** seam — the engine interface (`type Turn func(ctx, prompt, payload) (TurnResult, error)`) — injected at construction via `NewTurnDispatch`. Continuation logic (`continueReq` / `continueResp` / prompting) remains on **Model**, not on TurnDispatch.
- **Per-turn event timeline** — the single arrival-ordered event log (`message.events`) recording, in the exact order the model emits them, reasoning deltas, tool starts, tool results, and answer deltas for an assistant turn. `content` and `reasoning` are derived snapshots of that log — recomputed from it while streaming, finalized from the authoritative turn result at completion — so copy-to-clipboard, telemetry, and the OpenCode-gateway `tool_calls` export keep reading unchanged text. Both append seams write to the live `Transcript.timeline` during the turn (`TurnDispatch.appendStreamDelta` for stream deltas, `Transcript.apply` for tool observations); `handleTurnDone` commits it onto the turn's assistant message. In the live app the engine listener pushes both kinds onto one FIFO `EventFeed`, so the timeline records engine emission order rather than the arbitrary delivery order of Bubble Tea's parallel stream/tool wait commands (`tea.Batch` makes no ordering guarantee).
- **Merged transcript flow** — the transcript renderer walking the per-turn event log to emit one continuous block per turn in arrival order, replacing the three separate panes (thinking pane, tool log, answer pane). Reasoning reads as a dimmed left-ruled internal monologue (the `thinkingPaneStyle` / `streamingThinkingPaneStyle` frames, gated by the thinking toggle), tool starts and results render inline at the position their events arrive (pulling their rich entry state from the tool log by anchor, so inline expansion and elapsed timing survive), and the answer lands at the tail in its full-accent pane (or the dimmed streaming/error/stopped variants). `RenderFlow` (`internal/tui/flowrender.go`) is the single deep seam both the committed event log and the live timeline flow through: it folds the event list into named flow blocks (reasoning / tool / answer) and renders them, with the committed-vs-live difference (a committed turn emits one authoritative reasoning snapshot once; a live turn flushes each chain-of-thought fragment at the tool boundary it precedes) carried as a parameter rather than buried in closures — so the merged flow is unit-testable on a small event log with no Transcript/tool-log scaffolding. The Transcript's `renderEventFlow` is a thin delegate that assembles the `flowInput` (events, message snapshot, theme/view parameters, paired tool entries) and hands it to `RenderFlow`; turns with no event log (help/skill/login notes, error notes) fall back to the legacy blocks. The shared row→tool-entry hit-test index works on the merged stream unchanged because the flow records the same `toolRowRange` shape `toolLog.Render` produces. A committed turn's reasoning snapshot renders exactly once, at its first tool boundary (or the tail when no tool follows), never re-emitted at each tool boundary — so past turns stay scannable and any expanded turn replays its full interleaved reasoning/tool/answer sequence without duplication. On a live (streaming) turn the flow flushes each chain-of-thought fragment at the tool boundary it precedes (the same places `flushAnswer` flushes) and resets, so reasoning that resumes after a tool call renders as its own interleaved dimmed block between the tool entries — never dropped, never merged into the first block — while the committed path keeps the once-per-turn snapshot.
- **Phase** — the single derived answer to "what is the agent doing right now", computed on the TUI side (`internal/tui/phase.go`) from the live turn state rather than stored: the turn's busy flag plus what the in-progress assistant stream is doing. The four values are `idle` (no turn runs), `reasoning` (chain-of-thought is streaming before the answer begins), `working` (a turn runs but no assistant text streams yet — the tool-heavy gap), and `answering` (answer text is flowing; it takes precedence over trailing reasoning). Transcript's `phase()` is the seam the stage-label verb and the live-reasoning panel hang off; the busy indicator's stage verb splits by phase — `Reasoning` / `Working` / `Answering` under the spinner — while the reduced-motion/ASCII fallback stays the static `… thinking` line.
- **Live reasoning panel** — the current turn's reasoning block auto-expands while its chain-of-thought deltas stream, framed in the dimmed streaming thinking-pane border variant, so the user watches the thinking grow live instead of a static hint; it collapses back to the one-line `🤔 N tok` hint once the turn's answer lands. The expansion is computed at render time from the message's still-streaming state (`msg.streaming && msg.reasoning != ""`) rather than stored, so it needs no stream-exit reset: Enter on the Tab-focused block toggles it during and after streaming (collapsing a live block through the per-turn collapse override), and any reasoning the backend sneaks through a thinking-off turn stays hidden behind the `thinkingRequested` gate.
- **Collapse-by-default + block focus** — chain-of-thought and tool results collapse to their `🤔 N tok` hint / one-line call summary by default (two persisted Settings toggles, `CoTCollapsedByDefault` and `ToolResultsCollapsedByDefault`, both defaulting on), so a large reasoning block can never push tool calls out of view. Two Settings rows flip the defaults; the transcript stores the effective flags as `cotExpanded`/`toolResultsExpanded` (the inverse). Per-block expand is keyboard-driven: `Tab` cycles a `focusedBlock` cursor over the collapsible blocks (each turn's reasoning header then its tool entries, in flow order) and `Enter` toggles the focused block, with the `▸` marker on the focused head/hint. On a live turn whose chain-of-thought renders as multiple interleaved fragments (issue #449), each fragment is its own focusable block, so `Tab`/`Enter` collapse or expand a single fragment while the others keep their own state — the per-fragment force is scoped by fragment index and cleared on turn commit or global-mode entry. The global `e` key enters expand-all (clearing per-block collapse forces), `E` enters collapse-all-to-hints (clearing per-block expand forces), and `Ctrl+E` toggles between expand-all and the default mode; per-block forces beat any global mode so one block can always be shown or hidden. The `Expanded-view mode` and `Live reasoning panel` entries above are the prior pieces this folds together.
- **ExpansionState** — the value type (`internal/tui/expansion.go`, issue #468) that becomes the single owner of Eitri's block-expansion policy: the global `viewMode` plus a per-block expansion force for every collapsible block, reasoning fragments and tool-result entries alike. One query — `expanded(kind, id) bool` — answers whether a block renders open or collapsed: a per-block force beats any global mode, expand-all/collapse-all decide for a force-less block, and otherwise the block follows its kind's collapsed-by-default flag. The `toggle`/`set`/`clear`/`setMode` operations mutate that one policy source, and entering a global mode drops every per-block force so the mode rules uniformly. It holds no reference to transcripts or tool logs — callers map their own blocks onto ids — so it can be unit-tested as a state machine (mode × forces → open/collapsed) with no scaffolding. Issue #468 establishes the module and its test surface only (the "expand" half of the expand–contract). Issue #470 migrates the tool-log per-entry expansion onto the seam: the per-entry `expanded` / force-collapse flags live on a `toolLog`'s own `expansion ExpansionState` (forces keyed by the flat log index), every per-entry toggle/expand/force-collapse operation routes through the seam, and the expand-all / collapse-all toggles clear only the opposing direction (`clearForcesOf`) so a manually pinned force survives a mode round-trip. Issue #469 migrates the transcript reasoning-block expansion: each assistant message owns an `expansion ExpansionState` holding the reasoning block's forces — a whole-block force keyed on a callers-owned `reasoningWholeID` sentinel (the migrated `thinkingExpanded` / `thinkingCollapsed` flags) plus a per-fragment force for each interleaved fragment on a live turn, keyed by its emission-order index. The open/collapsed decision and every toggle (whole-block and per-fragment), plus the expand-all / collapse-all and turn-commit clear operations (`clearForcesOf` / `clearReasoningFragments`), read and write the seam instead of scattered leaf flags; the live-stream auto-expand still folded in at the call site (a streaming reasoning block stays open regardless of mode unless pinned force-collapsed). #471 completed the contract half of the expand–contract: the now-dead leaf helpers and their duplicate delegation (`toggleThinking`, `toggleCollapse`, and the `toolLog` `Toggle` / `ToggleCollapse` wrappers) are deleted — every caller toggles through the seam directly (`toggleThinkingFragment` for a reasoning block, `toggleToolEntry`, which pins `Expand`/`ForceCollapse` on the seam, for a tool entry) — and the `ExpansionState` table test is the single block-expansion test surface.
- **Collapse-focus seam** — the block-focus cursor state (issue #462) lives in its own module (`internal/tui/collapsefocus.go`): the `collapseFocus` value type owns whether the cursor is active and which collapsible block it points at (an index into a caller-supplied block list), with the Tab traversal as a state machine (`focusNext` activates/advances/wraps, and a zero-length list keeps it off) surfaced through one query (`focusedIndex`, plus the `focusedIs` match). The Transcript is a thin delegate: it renders its own model-dependent collapsible-block list onto the seam (`collapsibleBlocks()`) and forwards `focusNext`/`focused`/`toggleFocused`/`focusedBlockIs`/`focusedToolIdx` to the cursor position the seam reports, while the block identities and the expansion forces remain on `ExpansionState`. The seam is a pure value type — no reference to transcripts, messages, or tool logs — so the Tab-cycle/Enter-toggle cursor is unit-testable on its own with no Transcript scaffolding, completing the collapse+focus hand-off alongside the `Expanded-view mode` and `ExpansionState` pieces.
- **Markdown-rendered reasoning** — the expanded chain-of-thought block funnels through the same `RenderMarkdown` seam as the answer (at `transcriptWidth - 2`), so long single-line reasoning word-wraps instead of overflowing the terminal and code fences/lists keep their structure; the reasoning body frames in the `thinkingPaneStyle` / `streamingThinkingPaneStyle` dimmed-italic border so it reads as internal monologue next to the full-accent answer frame stacked below it. The collapsed-by-default behavior, the Enter-on-focused-block toggle, and the clipboard plain-text form are unchanged.
- **Tool-activity pulse fallback** — the busyPulse accent flash on tool starts while thinking is off: with no chain-of-thought stream to derive the arrival pulse from (the stream-delta pulse in `appendStreamDelta`), each tool beginning execution arms the same brief 3-frame accent pulse so the running (incomplete) tool entry's head flashes the agent accent instead of its category hue. The same armed pulse also flashes the bottom busy band (`bandStatusStyle` → accent while `busyPulse > 0`, back to the faint `statusStyle` once it expires), which is the only "something started" signal on a turn whose chain of thought is collapsed and whose tool card is not yet in view (issue #436). Gated to thinking-off turns (thinking-on already pulses via the stream) and to the motion gate, so the reduced-motion/ASCII fallback keeps the static `… thinking` indicator and the category-colored entries; a completed entry settles back to its category hue immediately.
