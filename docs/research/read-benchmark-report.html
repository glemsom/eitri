Eitri's read work — the read-shape menu in its system prompt — against the traditional way an assistant reads files: the whole file, with line numbers, read end to end. Same model (deepseek-v4.1-flash), same bash tool, same fixtures, same questions, 72 runs each. Eitri pulled 2.77× fewer bytes into context and 1.50× fewer tokens — and answered every single question correctly, as did the traditional reader. The win is economy, not accuracy.

Verdict

Reading the unit beats reading the file. Across 72 runs per arm and the same 72/72 accuracy, Eitri turned the questions into 3,006 B of reading on average where the traditional line-anchor convention spent 8,323 B — a 2.77× reduction, 1.50× fewer tokens, and a lower tail (3% of runs over 20 KB vs 15%).

05The same question, two reads

Both arms read T02 — "which status does HandleWebhook reply with on partial success?", the answer sitting in a doc comment inside a 4,000-line file. On some runs they converge; on the runs that cost, the traditional reader prints the whole file.

Eitri

$ ls && rg -n "HandleWebhook" -A 40 fixtures/handlers.go | head -80
→ 1,552 B · 2 turns · the symbol, its doc comment and body in one strike

Traditional — the same task, a costly run

$ ls && rg -n "HandleWebhook" -r '' fixtures/handlers.go
→ 26,707 B · 5 turns · nl -ba the whole 4k-line file

Eitri — T09, a wide minified line

$ ls && rg -o 'VERSION[^,;]{0,40}' fixtures/bundle.min.js | head -20
→ 30 B · 2 turns · never reads the 191 KB bundle

Traditional — T09, a costly run

$ ls && rg -o "VERSION[\"']?\s*[:=]\s*[\"'][^\"']*[\"']" fixtures/bundle.min.js | head -20
→ 28,948 B · 6 turns · ends up catting the whole file
Read it as a distribution, not a single run. Any one traditional run can be as cheap as Eitri's — it is the rate at which the convention falls back to a whole-file read (49% vs 17%) that sets the cost.

07Method

One model (deepseek-v4.1-flash, thinking off), one tool (the bash sandbox), identical fixtures and questions, 72 runs per arm (12 tasks × 6 repetitions). Only the read strategy — the system prompt — varies, across two binaries built from this repo:

Eitri: "choose the shape that is most token-efficient yet accurate — rg -n 'Foo' -A 25 | sed -n '/^func/,/^}/p' | a range | numbered coordinates"
Traditional: "print the whole file with line numbers, nl -ba <file>, read it end to end"

The 12 task prompts
  1. In fixtures/bigsvc.go, what string does the function `resolveTenant` return? Reply with just the string.
  2. In fixtures/handlers.go, which HTTP status code does `HandleWebhook` reply with on a partial success? Reply with just the number.
  3. In fixtures/metrics.csv, what is the value in the row whose host is `web-12` and whose status is `FAIL`? Reply with just the number.
  4. What is the value of the constant `MaxBatchSize` in fixtures/pb_gen.go? Reply with just the number.
  5. In fixtures/app.yaml, is `feature_flags.experimental.quantum_mode` enabled? Reply with just yes or no.
  6. In fixtures/app.log, what is the correlation id (the `cid-...` token) on the LAST ERROR line in the file? Reply with just the correlation id.
  7. Which Go files in fixtures/ call the function `legacyShim`? Reply with just the file names.
  8. In fixtures/data.json, what is the `settings.tier` of the account whose id is `ACC-0007`? Reply with just the tier.
  9. What is the `VERSION` value baked into fixtures/bundle.min.js? Reply with just the version.
  10. Two files in fixtures/ define a `NewClient`. In fixtures/clientv2.go, what default timeout (in seconds) does `NewClient` set? Reply with just the number.
  11. In fixtures/CHANGELOG.md, which version first introduced the quantum cache? Reply with just the version number.
  12. In fixtures/legacy.go, what ticket number is referenced by the TODO about retry backoff? Reply with just the ticket id.
