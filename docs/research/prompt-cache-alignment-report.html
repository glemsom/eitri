Eitri prompt-cache alignment

Cross-reference of Eitri’s cache-control and prompt-cache behavior against official OpenAI and Anthropic guidance.

Executive verdict

Verdict: Eitri aligns well with the universal prompt-shaping practices, but only partially with each provider’s protocol-specific cache controls. Its engine intentionally builds a byte-stable static head before the workspace directive, history, and current prompt. For OpenCode Go Chat Completions it then stamps an Anthropic-style cache breakpoint at the static boundary and at the moving tail. That is a sound design for a long-running agent: the stable setup can be reused across runs and the conversation can be extended incrementally.

The qualification matters. Eitri’s cache_control mechanism is an Anthropic-style extension carried through an OpenCode Chat-Completions gateway; it is not OpenAI’s native prompt-caching interface. Native OpenAI caching is automatic, and recent models expose prompt_cache_options and content-block prompt_cache_breakpoint, neither of which Eitri emits. Conversely, the provider path that actually serializes Anthropic Messages does not automatically apply Eitri’s otherwise thoughtful static-prefix/tail policy.

Bottom line: retain the current prompt ordering and OpenCode breakpoint strategy. To claim consistently strong alignment, first add and test automatic policy for Anthropic Messages, then make native OpenAI caching a deliberate capability rather than relying solely on provider defaults and telemetry.

What Eitri does

1. Constructs a cache-friendly prompt

The engine places the stable system-prompt head, skill index, and repository instructions before the per-run workspace directive, persisted history, and current user message. It records that stable count as StaticPrefixLen. This is documented in ARCHITECTURE.md and implemented in internal/engine/engine.go:247–267. It is exactly the high-value shared practice: make the reusable prefix immutable and move volatile values after it.

2. Uses two Anthropic-style cache breakpoints for OpenCode Chat Completions

internal/provider/chatdialect.go:222–238 copies the request and marks (a) the last static-prefix message and (b) the final message. The first boundary protects the setup from changing workspace state; the tail boundary seeds incremental reuse of a growing conversation. Eitri uses {"type":"ephemeral","ttl":"24h"}, sends prompt_cache_retention:"24h" for OpenCode Go, and uses the session GUID as prompt_cache_key (chatdialect.go:179–201; app.go:258–263).

3. Preserves cache-control in either wire dialect

Canonical Message and Tool values can carry CacheControl (internal/provider/provider.go:65–125). Chat Completions serializes it on messages/tools; Anthropic Maps it to compatible system/text blocks and tool definitions. This is useful transport capability, but it is not the same as a complete automatic policy.

4. Exposes a user-visible hit rate

Eitri normalizes several gateway usage shapes into prompt-cache hit/miss tokens and shows a cumulative cache percentage in the TUI. That follows the providers’ directive to measure actual outcomes. There is a correctness exception for OpenAI Responses zero-hit usage, described below.

Prioritized improvements

  1. High — implement cache policy for the Anthropic Messages dialect. Apply an automatic top-level or explicit marker policy equivalent to the static-prefix/tail design, using Anthropic-valid TTLs (5m by default, 1h when justified). Exercise it against the OpenCode models actually routed through anthropic.go. Ensure the total marker count stays at or below four.
  2. High — fix Responses zero-hit accounting. When cached_tokens is present but zero, normalize misses to total input tokens. Add a regression test and, if the data model permits, separately retain cache-write tokens. The current cache percentage can overstate efficiency by dropping cold input from its denominator.
  3. Medium — give native OpenAI caching an explicit capability model. Do not treat Anthropic-style cache_control as an OpenAI protocol feature. For supported native models, choose implicit versus explicit breakpoints intentionally; add prompt_cache_options only where the adapter/model supports it. Consider Responses prewarming only for known high-fan-out workloads, not ordinary single-user turns.
  4. Medium — define tool-marker precedence and test it. Keep the fixed tool manifest byte-stable. Decide whether an explicit tool marker should coexist with automatic message markers rather than disabling all automatic placement. Add wire-level tests for regular tool-enabled turns and provider-specific semantics.
  5. Medium — scope extensions by provider capability. Gate prompt_cache_key, 24h retention, and X-Opencode-Session to providers that document them. Make session-key use deliberate for native OpenAI: it can improve routing/accounting, but does not guarantee a hit.
  6. Low — harden model exclusions. Normalize model aliases before checking GLM/Zhipu exclusions, or preferably use provider/model capabilities instead of a case-sensitive substring guard.
